P0-01 — Remove cross-module Superadmin business imports

Problem

Several Superadmin features import business logic/types from the gyms module or other Superadmin modules. This breaks the documented “zero cross-module business dependency” model.

Confirmed examples

Invoices imports gymsApi and Tenant.

Features rollout UI imports gymsApi and Tenant.

Infrastructure tenant actions import gymsApi and Tenant.

Broadcasts imports gymsApi and Tenant.

Migrations imports TenantSchema from gyms.

Fix

For each consuming module:

Remove the business import from gyms.

Create that module's own local DTO/UI type under its own *_types/ folder.

Create a module-local API function if that feature needs a tenant lookup.

Do not create a new global shared business layer as a shortcut.

If a pure infrastructure primitive is truly shared, keep only dumb UI/shared primitives globally.

Re-run a grep for cross-feature imports after the change.

Acceptance test

src/app/superadmin/** must contain no imports from another Superadmin feature's API/type/schema/store unless the dependency is explicitly documented as an approved infrastructure primitive.

P0-02 — Stop using feature code as a mock-data source

Confirmed violations

Feature-owned mock-data files exist:

broadcasts/.../SuperadminBroadcastsMockData.ts

dashboard/.../SuperadminDashboardMockData.ts

global-audit/.../SuperadminGlobalAuditConstants is consumed by a handler as fake data

gyms/.../SuperadminGymsMockData.ts

Handlers also consume feature constants/mock data in multiple Superadmin modules.

Fix

Move fake response fixtures to src/mocks/handlers/** or a dedicated src/mocks/fixtures/superadmin/** area.

The feature API layer must describe the contract, not own fake backend records.

The UI must never use mock arrays as a fallback when the real API returns empty data.

Delete MOCK_GYMS-style UI fallback behavior.

Ensure empty API results render the proper empty state instead of substituting fake records.

Acceptance test

Disconnect/disable handlers and verify the UI does not silently manufacture business records.

P0-03 — Fix Broadcasts: it is not currently a real backend-style mutation flow

Confirmed problem

broadcasts contains local cache manipulation and hardcoded success toasts such as:

Broadcast updated successfully

Broadcast created successfully

Broadcast deleted successfully

Fix

Put every create/update/delete operation in broadcasts_api.

Call the API from a custom mutation hook.

Use the server response as the final source of truth.

Invalidate/update the relevant TanStack Query cache intentionally.

Surface the backend response message through the standard toast mechanism.

Remove hardcoded success messages from the component/hook.

Preserve form data when a mutation fails.

Prevent duplicate submission.

Acceptance test

The feature must still work if the mutation response contains a server-generated ID/timestamp or a different message.
